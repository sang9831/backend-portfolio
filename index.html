주문 정규화 · 조회 최적화 · 주문 생성 병목 개선

V34 정규화 및 V35 기준 구조에서 주문 목록·대시보드·주문 생성 스파이크 병목을 단계별로 해결했습니다.

1. 주문 테이블 정규화 (V34 · V35)

  • 문제: 주문 핵심 정보와 배송지·취소 이력이 혼재(29개 컬럼, 9개 인덱스)
  • 해결: 배송지·취소 1:1 분리 및 미사용 인덱스 제거(V34), 결제 만료 부분 인덱스를 배송 배치와 공유(V35)
  • 결과: 컬럼 29→17개(-41.4%), 인덱스 9→7개(-22.2%)
  • 근거: V35 d63e2b2 성능 #197

2. 판매자 주문 조회 최적화

  • 문제: 페이지 자르기 전 다수 주문의 결제 정보 조회 및 COUNT에서도 LATERAL 실행
  • 해결: 페이지 우선 조회 후 결제·취소 결합, 결제 상태 필터 미사용 시 단순 COUNT 분리
  • 결과: 주문 목록 2,080ms→49.44ms(-97.6%), 동시 상세 651.60ms→39.77ms(-93.9%)
  • 근거: 2681b75 성능 #201

3. 판매자 대시보드 최적화

  • 문제: 전체 후보 DROP마다 LATERAL 집계 및 요약 지표 5회 쿼리 분할 조회
  • 해결: 표시할 DROP 페이지 선별 후 통계 집계, 요약 쿼리 5회 호출을 단일 집계 쿼리로 통합
  • 결과: DROP 통계 10,770ms→280.92ms(-97.4%), 요약 7,500ms→362.20ms(-95.2%)
  • 근거: ede52c8 성능 #201

4. 주문 생성 병목 개선

  • 문제: 오픈 스파이크 시 drop_options 행 잠금을 먼저 잡은 채 주문·배송지·항목 INSERT를 수행해 직렬 대기 누적, DB 왕복 2회 및 풀 경합
  • 해결: findOptionSnapshots로 락 없이 단가 조회 후 주문·예약 INSERT를 먼저 수행하고 커밋 직전 마지막에 tryReserveOption(단일 조건부 UPDATE ... RETURNING) 실행, OrderCreationLimiter 상한을 HikariCP 풀 크기(10)에 맞춰 조정
  • 결과: V35 드롭 오픈 스파이크 주문 생성 p95 3,033.33ms→781.43ms(-74.2%, 거절 0건), DB 재고 왕복 2회→1회
  • 근거: 병목 #219 sang9831 후속 최적화

판매자 서류 암호화 저장과 운영자 열람 보호

파일별 데이터 암호화 키(DEK) 분리와 접근 이력 추적(워터마크·로그)을 구현했습니다.

서류 업로드 · DEK 생성 → AES-256-GCM 암호화 → 비공개 Storage → 마스터키로 DEK 암호화 → DB → 운영자 열람 · 복호화 · 워터마크 · 접근 로그

구현 방법 & 선택 이유

  • 업로드마다 고유 DEK 생성 후 서류를 AES-256-GCM으로 암호화
  • 서류 암호문은 비공개 Storage에, 마스터키로 암호화한 DEK는 DB에 분리 저장
  • 운영자 열람 시에만 복호화하며 워터마크 및 접근 로그 적용

구현 결과 & PR

  • 비공개 Storage 내 서류 암호문 안전 보관 확인
  • 운영자 열람 화면 워터마크 표시 및 접근 로그 DB 적재 확인
  • 관련 PR: #103 (암호화 저장) · #107 (열람·워터마크·로그)
